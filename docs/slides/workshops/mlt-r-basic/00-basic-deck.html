Build and validate a clinical ML model in R

Over the next ~4 hours we do one thing well: take a real clinical cohort (heart-failure clinical records, 299 patients), and build, tune, and validate a model that predicts in-hospital death — ending with a reproducible report a colleague can re-run.

  • The spine is tidymodels: rsample \(\to\) recipes \(\to\) parsnip \(\to\) workflows \(\to\) yardstick.
  • One outcome, four model families, one fair test-set evaluation.
  • Modular & incremental. Six short steps; each steps/NN/ folder is a complete snapshot, and the solution of one step is the start of the next — fall behind, copy the next folder, and you are back in sync.
  • Everything live-coded, everything reproducible (renv + here + set.seed).

The clinical question, and the cohort

The question. After a heart-failure episode, can routine baseline variables predict in-hospital death during follow-up?

The cohort. Heart-failure clinical records — 299 patients, 105 deaths (~32%), collected in 2015 (Faisalabad, Pakistan).

  • One row per patient; 13 columns = 12 clinical fields + the outcome DEATH_EVENT.
  • A real, open dataset — small enough to live-code, real enough to mislead you if you are careless (we will meet exactly one such trap: leakage).

Where to get it (free).

  • UCI ML Repository — Heart failure clinical records (2020).
  • Kaggle — Heart Failure Prediction (same data).
  • Citation: Chicco & Jurman (2020), BMC Med. Inform. Decis. Mak.

Voce docente (IT): nuova slide-dataset (richiesta esplicita). Cosa prevediamo, su chi, dove si scarica, come si cita. ~32% eventi (classe positiva = morte) — è il seme della scelta a due metriche più avanti. Anticipo la trappola del leakage (time), che risolviamo allo step 01.

The variables — 11 predictors, one outcome

Outcome — outcome: died / survived (we make died the first level, so every metric scores death as the positive class).

Predictors (11), grouped:

  • Demographics — age, sex.
  • Comorbidities — anaemia, diabetes, high_blood_pressure, smoking.
  • Labs & cardiac function — ejection_fraction (pump efficiency), serum_creatinine, serum_sodium, creatinine_phosphokinase, platelets.

Dropped on purpose — time (follow-up days): it leaks the outcome (longer follow-up is mechanically tied to who survives). Keeping it would inflate every score and fail in the clinic.

Voce docente (IT): le covariate, raggruppate per leggibilità clinica. ejection_fraction e serum_creatinine sono i predittori clinicamente forti (li ritroviamo nella VIMP dell’Advanced). Ribadisco il drop di time = leakage. 11 predittori + outcome = 12 colonne dopo il wrangle.

The tidyverse — one grammar for data

A family of packages that share one design: a tidy tibble goes in, a tidy tibble comes out.

  • A tibble is a data frame that prints cleanly and never surprises you (no silent type coercions, no row names).
  • Every verb returns a new tibble — it does not edit in place. You build a result by chaining verbs, then assign once with <-.
  • One consistent style across dplyr, tidyr, ggplot2, … — learn the grammar once, reuse it everywhere.

Artwork by Allison Horst (CC BY 4.0)

Voce docente (IT): cos’è il tidyverse e il modello mentale chiave = funzioni pure che ritornano una NUOVA tibble (niente modifica in-place). Questo prepara il “your turn”: si concatena e si assegna una volta sola.

The native pipe |>

The pipe sends the value on its left into the first argument of the function on its right. It turns inside-out nesting into a left-to-right recipe.

x |> f() |> g() is g(f(x)) — but you read it in the order it happens.

hf_raw |>
  clean_names() |>
  select(-time) |>
  glimpse()

Read it aloud: take the raw data, then clean the names, then drop time, then look. No temporary variables, no nested parentheses.

Reshaping with verbs — dplyr, janitor, forcats

A handful of verbs do almost all of wrangling:

  • select() — keep / drop columns (e.g. select(-time)).
  • mutate() — add or change columns (e.g. build outcome).
  • filter() — keep rows by a condition.
  • across() — apply one transform to many columns at once.
  • janitor::clean_names() — tidy, snake_case, machine-safe column names.
  • factor() / forcats — turn text into a factor with explicit levels; we set died first so it is the positive class everywhere.

Tidy data — and the leakage trap

Tidy data art: Lowndes & Horst, Openscapes (CC BY 4.0)

Tidy data: each variable is a column, each observation a row, each cell one value. Tidy in \(\to\) everything downstream just works.

Leakage: a predictor that secretly encodes the outcome. Here time (follow-up days) is mechanically longer for survivors — a model that uses it “predicts” death by cheating, scores beautifully in the slides, and fails in the clinic.

  • The fix is one line — select(-time) — but spotting leakage is a clinical-judgement skill, not a coding one. Always ask: could this column only be known after the outcome?

Voce docente (IT): tidy data (1 var/colonna, 1 oss/riga, 1 valore/cella) + la mini-lezione di LEAKAGE che giustifica il drop di time. Il messaggio forte: il leakage si riconosce col ragionamento clinico, non col codice.

Where today’s model fits — learning paradigms

Today we do supervised learning: every patient carries a known label (died / survived) and the model learns the mapping from features to label.

  • Supervised — labelled outcome; classification (our case) or regression. ← today
  • Unsupervised — no labels; find structure (clustering, PCA). You met it in the Overview; out of scope here so we can do one supervised pipeline thoroughly.
  • Reinforcement — an agent learns from rewards by acting, not from a table of labels (think treatment policies that improve with feedback).
  • Active / online — the model asks for the most useful next label, or keeps learning as data streams in.

One labelled table, one clear target: that is why supervised methods fit this problem.

tidymodels — one spine, five packages

tidymodels is the tidyverse for modelling: the same five-package spine fits any algorithm. Learn it once on a logistic regression; reuse it for the whole zoo.

  • You declare what you want (a model spec), not how each engine wants its inputs.
  • Swapping algorithm = changing one line (the parsnip spec). Everything else holds.
  • Because the recipe and model travel together in a workflow, preprocessing can never leak from test into train.

Hyperparameters, one algorithm at a time

A hyperparameter is a setting you fix before fitting — unlike the ordinary parameters (coefficients, split points) that the fit learns from the data. Same spine, one hyperparameter at a time: what it is \(\to\) what it controls \(\to\) its effect on bias / variance / overfitting.

Voce docente (IT): le 4 slide-iperparametro precedono il tuning. Definisco subito “iperparametro” (scelto prima del fit) vs “parametro” (appreso) — così rispondo al “perché non chiamarli iperparametri”: ora li chiamiamo così. Una slide ~4 min ciascuna, non si tuna ancora nulla.

Penalized logistic — penalty / mixture

The glm baseline, regularized: shrink coefficients to trade a little bias for much less variance.

hyperparameter what it means effect
penalty (\(\lambda\)) strength of shrinkage toward 0 \(\uparrow\) penalty \(\to\) more bias, less variance (guards overfit); too high \(\to\) underfit
mixture (\(\alpha\)) ridge \(\leftrightarrow\) lasso dial 0 = ridge (shrink all); 1 = lasso (some coefs \(\to\) exactly 0, selects); in between = elastic-net
  • Engine glmnet; both left as tune() in the workflow_set.

Voce docente (IT): collega al glm dello step 03 — “stesso modello, con un freno”. mixture sceglie come si penalizza (ridge/lasso/elastic-net); lasso fa anche selezione (coef esattamente 0). Tolto il bullet-slogan; mantenuto engine + tune.

\(k\)-NN — neighbors

Predict from the \(k\) closest patients. The single hyperparameter neighbors is the bias–variance dial.

neighbors (\(k\)) behaviour bias / variance
small \(k\) (e.g. 1–3) follows local noise, jagged boundary low bias, high variance (overfits)
large \(k\) averages over many neighbours, smooth boundary high bias, low variance (can underfit)
  • Range. \(k\) runs from \(1\) to \(n_{\text{train}}\): at \(k = 1\) it memorizes, at \(k \to n\) it just predicts the majority class. The good value is interior, so we tune it.
  • Engine kknn; neighbors left as tune().

Voce docente (IT): qui atterra la MCQ del min 118 (direzione bias-variance di k). Tolto il bullet-slogan (“più k sempre meglio”/“solo velocità”); aggiunto il RANGE 1..n_train e l’idea che l’ottimo è interno → si tuna. Engine + tune come gli altri.

SVM (RBF) — cost / rbf_sigma

Separate the classes with a margin; the RBF kernel lets the boundary curve.

hyperparameter what it means effect
cost (\(C\)) penalty for margin violations \(\uparrow\) cost \(\to\) harder margin, fits training tighter \(\to\) lower bias, higher variance
rbf_sigma (\(\sigma\)) how fast a patient’s influence fades with distance see below

rbf_sigma, in words. The RBF kernel rates two patients by a similarity that fades with distance; \(\sigma\) sets how fast it fades. Small \(\sigma\) \(\to\) influence reaches far \(\to\) a smooth, almost-linear boundary (more bias). Large \(\sigma\) \(\to\) influence is very local \(\to\) the boundary wiggles around individual points (more variance, overfit risk).

  • Engine kernlab; cost and rbf_sigma are tune()d together (they interact).

Voce docente (IT): CORREZIONE rispetto alla versione precedente — la direzione di rbf_sigma era invertita. In kernlab il kernel è \(\exp(-\sigma\,\lVert x-x'\rVert^2)\): \(\sigma\) ALTO = decadimento rapido = influenza LOCALE = confine ondulato = più varianza; \(\sigma\) BASSO = portata ampia = confine liscio = più bias. Spiegato a parole come chiesto.

Random forest — mtry / min_n / trees

Many decorrelated trees, averaged. Two hyperparameters we tune — and one quantity we just set large enough.

setting what it means effect
mtry predictors offered at each split small mtry \(\to\) trees more decorrelated \(\to\) lower variance; large \(\to\) trees agree more
min_n minimum samples in a leaf large min_n \(\to\) shallower, simpler trees (more bias, less variance)
trees number of trees a convergence quantity, not a tuning dial — see below

trees is not a hyperparameter to tune. More trees never overfit; they only shrink Monte-Carlo noise until the averaged prediction converges. Cost grows linearly with trees, so the only task is to set it large enough to have converged — bigger than that is wasted compute, not better accuracy. A converged-but-oversized forest needs no refit at a smaller value (the answer won’t change); you’d revisit trees only if the problem itself changes. So we tune mtry / min_n and merely fix trees large.

  • Engine ranger; mtry and min_n are tune()d, trees is set (not tuned).

Voce docente (IT): punto chiave (e accordo con l’utente) — trees NON è una manopola di overfit né da tunare: è una quantità di CONVERGENZA. Costo lineare nei trees → metterne “ancora di più” è inutile; basta garantire la convergenza. Non si riaddestra più piccolo se era sovradimensionato (stesso risultato); si rivede solo se cambia il problema.

Tuning machinery — workflow_set, tune_grid, CV

  • vfold_cv(v = 5) splits train into 5 folds; each model is scored on each held-out fold and averaged — an honest estimate that never touches the test set.
  • workflow_set() bundles {one recipe} × {four specs} into four workflows at once.
  • workflow_map("tune_grid", grid = 8) tries 8 hyperparameter combos per model over the folds, scoring both metrics.
  • rank_results() / autoplot() compare; select_best() + finalize_workflow() lock the winner’s settings; last_fit() trains on all of train and scores once on test.

Two metrics — and why a single split lies

Why two. With a ~32%-event outcome, “always predict survived” is ~68% accurate and clinically useless. We watch two complementary numbers:

  • AUC-ROC — ranking of risk across all thresholds; prevalence-free, chance \(= 0.5\).
  • AUC-PR — performance on the positive (death) class; its no-skill baseline is the prevalence (\(\approx 0.32\)), so it stays meaningful when the event is rare.

Why cross-validate. A single ~75-patient test split is high-variance: by luck it can flatter a weak model — even make a plain glm look unbeatable — while 5-fold CV, which averages over five held-out slices, gives the honest comparison. Across the zoo the random forest typically leads on CV while the linear models trail; the test set then confirms the finalized winner once.

Numbers are read live. Exact AUCs depend on the seed and the run, so we read them from the live execution, not from the slide. What is stable is the pattern: cross-validation is the honest ranking, and one number on a small cohort is luck.

Aside (no numbers needed). AUC-ROC is symmetric — the positive class doesn’t change it. AUC-PR is not: it depends on the positive class, which is exactly why we put died first, so both metrics score death by default. Moving the decision threshold by a clinical false-negative / false-positive cost ratio is a deliberate Advanced topic; here we stop at threshold-free ranking.

Why “one render” is reproducibility

A report whose numbers are typed in — or reloaded from a stale cache — can silently disagree with the analysis. A .qmd that executes the analysis as it renders guarantees the figures and the code that made them are the same object. That is the whole point of a literate, executable document.

  • renv pins the packages, here the paths, set.seed the randomness \(\to\) same inputs, same output, on any machine.
  • What about speed and big analyses? At N=299 a full tune is seconds. When an analysis gets heavy you don’t hand-cache .rds files — you reach for a pipeline (targets, the Advanced capstone) that caches and stays reproducible: inspectable intermediate targets, each re-derivable and hash-checked, all converging into the report the pipeline compiles itself.
