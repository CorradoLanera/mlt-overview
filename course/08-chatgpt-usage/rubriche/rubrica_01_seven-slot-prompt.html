Rubric — Item 01 (Build a 7-slot prompt: surgical-procedure extraction)

Item: IB-08-chatgpt-usage-01 Objective: Construct a structured prompt for a given clinical task using the 7-slot template, justify each slot's contribution by naming the specific failure mode it suppresses, and reason about which slots are most and least load-bearing for this specific task (Obj. 1).

The rubric scores three criteria, one per sub-question, on three levels — Base (sufficiency floor), Good (solid command), Excellent (task-specific reasoning that distinguishes this task from any other).

Criterion Base Good Excellent
C1 — 7-slot prompt construction (sub-q 1) All seven slots filled, each with task-specific content (no generic boilerplate, no re-wording of the slot's own definition). The slot named task contains one verb (not two or three). The slot named examples contains at least one input/output pair, not just a description of what examples would look like. All of Base, plus two key escapes are present: (i) the output slot includes an explicit escape token for the ambiguous case — e.g. 'UNCLEAR', '', 'NA' (any sentinel that the audit script can branch on); (ii) the style slot explicitly forbids the model from adding explanation, qualifications or preamble. All of Good, plus the instructions slot contains a disambiguation rule for multi-procedure notes — e.g. "if multiple procedures are named, return the one listed first under the 'procedure performed' heading" (or any equivalent priority rule). This rule is what stops two correctors from disagreeing on the same operative note, and recognising the need for it signals chapter-level fluency on the one-verb discipline of the task slot.
C2 — Failure-mode justification for role, style, examples (sub-q 2) For each of role, style and examples, the student names a concrete, namable wrong behaviour the model would exhibit without that slot. Vague phrasings such as "makes the answer better", "clarifies the request", "the model would be confused" are below Base — they describe an effect on the student's reading, not on the model's output. The failure mode must be operational: a string the model would produce, a behaviour an audit script could detect. All of Base, plus the three failure modes named are distinct from each other — the student names a different concrete behaviour for role (voice/register), style (formatting/preamble) and examples (edge-case handling), and does not collapse two slots into "the model would explain too much" twice. All of Good, plus the student names, for at least one of the three slots, the specific failure mode for an extraction task (not for a generic clinical task) — e.g. for examples, that the model would drift on converted procedures ("started laparoscopic, converted to open") or staged procedures, naming an actual pattern in operative-note writing. The justification is task-aware, not slot-agnostic.
C3 — Most/least load-bearing slots for this task (sub-q 3) Names one slot for most and one slot for least, each with a one-sentence justification. Most: output or task (both acceptable). Least: any of role, context, or style with a defensible reason tied to the specifics of procedure extraction. Naming output or task as least load-bearing is below Base — this is the single non-negotiable misreading of the task. All of Base, plus the justification for the least slot names what that slot would contribute on a different task (e.g. "role is least load-bearing here because the structured output already enforces voice; on a patient-facing leaflet, role would be the most important slot"). The student recognises that load-bearing is task-relative, not slot-intrinsic. All of Good, plus the most load-bearing justification names the downstream consequence of removal — not just what the model would produce but what would break in the audit: e.g. "without output, the model would return prose on the majority of notes; the audit script that aggregates labels would silently miscount every prose response as a unique procedure, distorting the audit at scale". The student is reasoning about the system, not just the model.

Soglia di sufficienza: tutti e tre C1, C2 e C3 a livello Base o superiore. La filling di meno di 7 slot, una giustificazione vaga su anche uno solo dei tre slot di C2 (role / style / examples), o nominare output / task come least load-bearing in C3, equivalgono a non aver svolto l'esercizio: l'item misura la capacità di costruire e ragionare sul template a sette pezzi, non la capacità di nominare i sette pezzi.

Bias da evitare in correzione:

  • Premiare la lunghezza in sub-q 1. Una scheda 7-slot ben fatta sta in sotto-mezza pagina; uno studente che riempie ciascun slot con un paragrafo non sta facendo meglio, sta facendo prompting peggiore — un prompt più lungo non è un prompt migliore, e di solito è un prompt che il modello segue con più drift, non con meno. Valutare correttezza e specificità del contenuto di ogni slot, non la sua lunghezza.
  • Non confondere "ha nominato un failure mode" con "ha nominato il failure mode giusto". In C2 l'errore tipico è scrivere "il modello potrebbe sbagliare" — è una risposta a un'altra domanda. Il prompt strutturato non risolve "il modello potrebbe sbagliare" (è il problema generale); risolve failure mode specifici e prevedibili. Lo studente che scrive "potrebbe sbagliare" è sotto Base.
  • Non premiare giustificazioni generiche per i sette slot. "Role serve a chiarire chi parla" è una rifrasatura della definizione di role, non una giustificazione del failure mode che sopprime — è sotto Base. Pretendere il cosa farebbe il modello senza quel slot, esibito come stringa o comportamento osservabile.
  • Non scambiare least load-bearing con inutile. In C3, dire che role è least load-bearing per questo task non equivale a dire che role sia inutile — il livello Good premia esplicitamente lo studente che fa questa distinzione (nominando in che task role sarebbe invece most load-bearing). Studenti che leggono "least load-bearing" come "da eliminare dal prompt" stanno fraintendendo la regola, non l'esempio. Correggere indicando che il 7-slot va sempre riempito tutto; la domanda è su quale slot è marginale, non quale slot è ridondante.
  • CRITICO — non penalizzare la scelta di task o output come most load-bearing. Entrambe sono accettabili a Base purché la giustificazione sia coerente. Output è la scelta più semantica al risultato (la forma del deliverable rompe la pipeline se assente); task è la scelta più semantica al processo (il verbo rompe l'intento). Lo studente che sa argomentare l'una o l'altra è a Base; lo studente che le confronta esplicitamente è a Excellent. Penalizzare una sola delle due in favore dell'altra è imporre una preferenza personale del correttore, non misurare l'obiettivo.
  • Non accettare un terzo slot al posto di uno dei due richiesti. La sub-question 3 chiede uno per most e uno per least; uno studente che ne nomina tre o quattro ("output, task, instructions sono tutti most...") non sta rispondendo alla domanda — l'esercizio è di priorizzazione, non di enumerazione. Riportare a one most + one least, ed eventualmente classificare la performance del priority call come Base anche se le tre opzioni nominate sono tutte legittime in sé.
